# Allay for Minecraft: notes for AI agents

The Minecraft plugin and the Fabric and NeoForge mods of Allay. `/ask` asks the AI helper a question, `/askall` asks in front of everyone, `/askx` turns a request into commands, and chat mode (`/allay chat`) sends whatever a player writes in chat to Allay. The plugin streams the answer from Allay Server (allay-ai/server) over protocol v2, runs the game tools the agent asks for, and shows a live Claude Code style status while it works. README.md is the shop window (what Allay gives, how to start, links), README.RU.md its Russian copy, MODRINTH.md the Modrinth page. The manual for players, server owners, and developers is the GitHub wiki (https://github.com/allay-ai/minecraft/wiki, English only, cloned from `allay-ai/minecraft.wiki.git`); read it first.

## Talking to the owner

- Reply in Russian, address the owner as «вы». Quotes «ёлочки», an em dash with spaces « — ».
- Code, comments, commit messages, and `config.yml` are in English. Player-facing texts live in `core/src/main/resources/lang/<code>.yml` (en, ru, es, pt, de); a new text goes into every one of them, and `LangTest` checks that each has every English key. README.md is English; README.RU.md follows Russian typography. Change both READMEs and MODRINTH.md together. A new command, permission, config key, or feature also goes into its wiki page (“Commands and permissions”, “Configuration”, and so on).

## How it fits together

Six Gradle modules. `expansion` is the expansion API other plugins and mods build against (see “The expansion API” below). `core` holds everything that doesn't touch a game platform and never imports `org.bukkit` or `net.minecraft`: the whole flow of a question, the commands, chat mode, billing, memory, privacy, the agents' wakes, and the tools that need no world. `spigot` is the plugin for Spigot, Paper, and their forks, an adapter around `core`: it hands in a `Platform` and a `Game` and forwards Bukkit's events and commands. `modcore` is what both mods share, the game without a loader, and `fabric` and `neoforge` are the mods, thin adapters around it (see “Mods” below). The wiki's “Architecture” says what a new platform must bring.

## The expansion API

`expansion/` is `chat.allay:allay-expansion`, the library other plugins and mods build against, on Maven Central since 1.0.0 (Allay 6.12). The owner settled its design on 2026-10-24; the wiki's “Expansions” is its manual for authors.

- **Plain Java, no dependencies, Java 21 bytecode**, so any plugin or mod can use it and Allay's Kotlin stays private. Every Allay jar carries its classes unrelocated through `core`'s `api(project(":expansion"))`; never relocate `chat.allay.expansion`, and authors use `compileOnly`.
- **Its own version.** `AllayApi.VERSION` is the library's version and what `requiresApi()` returns; `expansion/CHANGELOG.md` its notes. Within a major the API only grows: a new interface method comes with a default, and nothing is removed or changes meaning. Allay refuses an expansion that needs a newer minor or another major, with a line in the log.
- **Releasing** is its own workflow, `gh workflow run expansion.yml -R allay-ai/minecraft -f version=X.Y.Z`, after `AllayApi.VERSION` and `expansion/CHANGELOG.md` say that version. It signs with the `MAVEN_SIGNING_*` secrets, uploads through `tools/central.py` with `publishingType=AUTOMATIC` (no draft to click), waits for `PUBLISHED` and repo1.maven.org, and tags `expansion-vX.Y.Z`. A version goes to Central once and stays. The key and the token live in `secrets.toml` in MairwunNx/infrastructure (`[publishing]`) and reach this repository through its `github.toml`.
- **Security.** An expansion's tool runs only in a run that offered it (`Run.expansionTools`, set on the server thread in `Handler.ask`, after the consent gate), never for the console or an automation agent; `OPERATOR` tools are offered to operators only and checked again in `Expansions.run`; only `READ` tools in `/askx`; `inPublic` decides public questions; the author's `permission()` is asked with `can(permission, byDefault = true)`. Results are cut at 8000 characters, descriptions at 1000, schemas at 4000, prompts at 2000. The backend frames descriptions and prompt lines as the plugin's and keeps Allay's rules above them; keep both sides doing so.
- **Protocol.** `expansion_tools` and `expansions` in the chat request (backend 6.14, `docs/protocol-v2.md` “Expansions”); a call comes back as a plain `tool_call` with the tool's name.
- Nothing needs an expansion to be found: mods' items and recipes, data packs' recipes and brews, and plugins' items built on the game's own with a model of their own come from the server itself (`Catalog`). An expansion is for tools, prompt lines, and what the server can't show (a Paper potion mix that matches by code). The game tests' `CatalogGameTests` register an expansion of their own, and the wiki's “Expansions” has one for each platform.

## Coming from MCBuddy

Allay was MCBuddy until 4.0.0. Since 6.7 the plugin no longer moves `plugins/mcbuddy-spigot/` by itself: a server coming straight from MCBuddy runs Allay 6.6 once first. The backend still accepts the 3.x tool names `get_buddy_guide` and `buddy_settings`.

## Rules that keep it working

- Spigot API only (`org.spigotmc:spigot-api`), so the jar runs on Spigot and Paper. Watch for types that differ between them: `GameRule` is an interface in Spigot and a class in Paper, so read rules through `Registry.GAME_RULE`. One exception: Paper leaves out Spigot's dialog API (BungeeCord's `net.md_5.bungee.api.dialog`), so windows (`Window` in core) go through `Windows`, which draws them with `spigot/src/paper/` (compiled against paper-api, loaded only on Paper) or with Spigot's API elsewhere. A dialog that doesn't pause the game: `NONE` after an action needs `pause(false)`.
- Bukkit calls happen on the server thread; network calls never do. Chat arrives off it: `ChatMode` only decides and cancels there, then hands the line to the server thread.
- A player's own words go into a template through `Minecraft.withText`, so an `&` they typed never becomes a color.
- PlaceholderAPI goes through `{papi:…}` in the template only, filled in `Lang.fill`'s single pass. Never run `%…%` replacement over a finished line: a player's question or the model's answer could then read other players' data through PlaceholderAPI. `%allay_…%` may be asked from TAB's thread, so it reads only thread-safe state.
- A vanished player never shows through Allay to anyone but themself and operators: anything that counts, names, sees, or completes players goes through `Vanish.visible` (on the server thread, where metadata lives). Their public question goes private (`Handler.ask`), since everyone would read their name. An operator tool may still target them by name.
- Containers reach the model, and glow, only when the asker could open them (`Claims.mayOpen`): outside a GriefPrevention claim or with container trust in it, and never an unopened structure chest, which Paper's anti-xray hides. Every tool that reads or marks a container asks it.
- Redstone and drafts read the world only where the asker may build (`Claims.mayBuild`: outside claims, or with build trust). A draft lives in memory (`Drafts`), one per player, drawn with the same display entities as marks; its size limit (20×15×20) is the owner's, so the model can write it.
- Marks (`Marks`, `show_marks`) are display entities: hidden by default and shown to the asker alone, never persistent, gone on time, `/allay cancel`, quit, and disable. They glow through walls, so `Marks.secret` (ores, spawners, vaults) never glows; keep that list in step with what anti-xray hides.
- Other players reach the model only through `Locator`, the game's locator bar rules (26.3's `ServerWaypointManager` and `WaypointTransmitter`): a name, a distance, and a direction, for players on the asker's bar. The owner allowed exactly that, since the player sees it anyway; never add their coordinates, inventories, or anything the bar doesn't show. Read the rules again from the jar when the game version moves.
- A tool that creates items or changes the world is an operator tool (`operator = true`). The registry offers it only to operators, `Service` refuses it for anyone else, and the tool checks `isOp()` once more. Keep all three checks; non-operators must not be able to get gear through the assistant.
- Automation is the owner's other exception: its tools move and craft for non-operators, but only the player's own things. They touch only containers `Claims.mayOpen` allows, and furnaces, stands, and crafting tables within `automation.radius` and in plain sight (`Blocks.sees`: only a block Bukkit calls occluding hides it; glass, leaves, slabs, sea lanterns, and the like let the view through). Crafting needs a real crafting table and uses server recipes with plain ingredients only; nothing comes from nowhere. Never inside shulker box items (a placed shulker box is a chest like any other, and takes no shulker box). Chests open in someone's window stay out; chests with a hopper on them (a sorter's input) only take things in: `Blocks.unsuitable(adding = true)`. Water bottles come only from the player's glass bottles at water or a cauldron near, which loses a level a bottle, as in the game.
- Chest changes are planned in memory, checked (totals equal, everything fits, nothing changed since the read), and written in one tick; otherwise nothing moves. Keep `Storage` the only place that plans them, with its tests. `Undo` keeps each player's last five changes, chest plans and inventory sorts, and puts back the newest only while nothing it touched changed.
- Furnace experience goes to the player only when the furnace's store can be emptied (`setRecipesUsed`, Paper); on Spigot it stays in the furnace, so it's never paid twice.
- An agent never gets operator tools (`Service` drops them for task runs and refuses them again). Whatever it plans to take later goes into `Reservations`; when it's gone at the next step, the agent stops and tells the player (`Automation.interfered`).
- Buttons in answers come from the model's text, so treat them as untrusted: `InteractTools.fromTag` checks each as the old tool did, and a tag that fails shows as its label. A `command` button (runs as the presser, minus `blocked_commands`) and a `say` button (sends its text to the public chat as the presser, once, never a line starting with `/`) work only in private answers; in an answer everyone reads they stay labels, so nobody can talk Allay into a `/trust` button for everyone. Chat mode lets a say button's line through (`ChatMode.say`).
- One deliberate exception: `[Взять книгу]` gives anyone the written book with the assistant's own long answer, once per book. The owner allowed it: a book of text is no gear. Don't extend it to other items.
- Windows (`menus/`) only show pictures. `MenuListener` cancels every click, drag, and hopper move on a `Menu`; keep it that way, or the windows become a dupe.
- Buttons run `/allay do <id>`. Ids belong to the player who got them (`ButtonStore`) and expire after an hour, so a typed command can't trigger an action nobody offered.
- Never let the model's memory settle whether a thing exists: `search_items`, `get_recipes`, and brewing read the server (`Catalog`). A refusal never says “doesn't exist”; it names what this server has under close names, so the model can look again.
- Keep tool results compact: they cost tokens on every call. Spots are absolute `x`, `y`, `z` with `distance` and `direction` (`Facts.place`); dimensions are the game's ids through `Dimensions`.
- Kotlin, kotlinx, OkHttp, Okio, the MaxMind reader, and SnakeYAML are shaded and relocated under `chat.allay.libs`.
- Every request to the backend signs in (server 6.0): keep `Credentials` on the client as a network interceptor, so nothing goes to another host, redirects included. A new backend call goes through that client. A player's data is the backend's per server; the plugin never sends one player's id for another.
- Nothing about a player reaches the backend before they agree to the notice (`Consents` in core, the gate at the top of `Handler.ask`, the notice in `PrivacyCommands`); every way to ask goes through `Handler.ask`. The agreement carries the SHA-256 of the English notice as the jar ships it and the backend's policy revision (6.9): a change to either asks everyone again, with a notice that says what changed; raise `Consents.VERSION` too when the notice says something new. The notice and the age question are windows (`PrivacyCommands`), with one line in chat to open them again. A player from the EU, the EEA, or the US, or from an unknown country, first says their age in neutral bands (`AgeGate.asks`; the owner chose to spare everyone else); it must reach their country's age of consent (GDPR Art. 8, LOPDGDD Art. 7, COPPA; 16 when the country is unknown). The agreement goes with `age_confirmed`, and one without it asks such a player again; too young keeps only a sealed note in `ages.bin` for a year. With allay.chat (no `server.token`) neither `privacy.consent` nor `geoip.enabled` may skip any of it.
- Other players reach the model by name only when they agreed on this server (`consented.bin`); anyone else is “Player N” for the run (`OtherPlayers`, `ToolContext.nameOf` and `playerNamed`). A new tool that names another player goes through `nameOf`.
- Full privacy (`Settings.full_privacy`, `/allay privacy full`, the `/allay` window) goes with every question as `player.private` and, for a player who agreed, to `PUT /api/v2/users/{id}/privacy` at once (backend 6.5): the admin panel then knows them by pseudonym only. It hides nothing from the model; memories and the session work as before.
- A player's data on request: `/allay privacy`. An export is a 24-hour link from the backend (6.9), shown only to whoever asked, never in the log; the log never says who asked to be erased.
- No personal data in the plugin's folder (since 6.7). `PlayerData` (core) holds each player's time zone, settings, and goals in memory while they play: it loads them from the backend when a player on `consented.bin` joins (the sealed list of UUIDs that agreed here; nobody else is looked up until they use Allay), sends a change a few seconds later, on quit, and at shutdown, and sends each death as it happens, all off the server thread. Nothing reaches the backend for a player who didn't agree, and their changes leave with them. What can't be sent at shutdown goes into `pending.bin`, AES-256-GCM under a key derived from the license or `server.token`, and out on the next start. A new per-player setting goes into `PlayerState`, never into a file.
- Never log, print, or put into chat the BYOK key, the license, or `server.token`. Mask them with `Secrets.mask` (first 5 and last 4 characters at most) and pass error texts through `Credentials.scrub`. The payment link goes only to the chat of whoever ran `/allay link`, and the admin panel's setup link only to whoever ran `/allay init`; the console's own output is the exception, since the console asked. `license.key` stays out of `config.yml` and is owner-only; never overwrite one that holds something else.
- Billing errors read light and never blame the player (“Allay is taking a break on this server…”); operators get the fix under them. Never show dollars: the subscription's limit is a percentage.
- `core` never imports `org.bukkit` or `net.minecraft`. Where it needs the game, it asks through `Platform`, `Audience`, `Allay.Game`, `Host`, or `ItemData`. Anything that doesn't touch the world goes into `core`, so the mods get it for free; a new Bukkit-only piece needs a reason it can't live there.
- Every platform reports `loader` (`spigot`, `fabric`, `neoforge`) and `side` (`server`; `integrated` for a mod in singleplayer or LAN) through `Allay.Game`; the backend shows them and tells the model, and makes a license from a player's own game Solo (backend 6.12). A Solo license answers one player and refuses the rest with `SOLO_PLAYER_TAKEN`.

## Building and releasing

- `./gradlew build` runs every module's tests, both mods' game tests included, and builds `spigot/build/libs/allay-spigot-<version>.jar`, `fabric/build/libs/allay-fabric-<version>.jar`, and `neoforge/build/libs/allay-neoforge-<version>.jar`, all shaded; Java 25. Nothing in the repo holds the version: local builds are `dev`, CI builds on `master` and pull requests are `dev-<sha>`; FML wants a number, so the NeoForge jar says `0.0.0-dev` (`0.0.0-dev-<sha>`), and `OnNeoForge.version` drops the `0.0.0-` again.
- Allay sounds like an allay: `ENTITY_ALLAY_AMBIENT_WITH_ITEM` while thinking, `ENTITY_ALLAY_ITEM_GIVEN` with the answer, `ENTITY_ALLAY_AMBIENT_WITHOUT_ITEM` on errors, each pitch moved by up to `ui.sounds.pitch_variation`. Readers of a public answer hear the answer sound at half volume (`ui.sounds.public_answer`). The game plays these quietly, so 1.0 is the mob's own volume.
- After a change that reaches what the project ships, add it to CHANGELOG.md in the same push: under the topmost “## X.Y.Z” section while that version isn't released (`gh release view vX.Y.Z` fails), or under a new section with the next version: patch for fixes, minor for features, major for breaking changes. A release then needs only the workflow, and the workflow runs only when the owner asks.
- Releases are made by hand when the owner asks, or by the autopilot (below). Add a “## X.Y.Z” section to CHANGELOG.md, push, then run `gh workflow run release.yml -R allay-ai/minecraft -f version=X.Y.Z` (its `changelog` field overrides the section; one of the two must be there; `-f modrinth=true -f hangar=true` also publish there once those projects exist). It builds with `-PreleaseVersion`, tags `vX.Y.Z`, and attaches `allay-spigot-X.Y.Z.jar`, `allay-fabric-X.Y.Z.jar`, and `allay-neoforge-X.Y.Z.jar` to a GitHub release, each also without its version. Watch it with `gh run watch`. Never delete or re-tag a published release.

## Checking a change

1. `./gradlew build`: the tests and the jar.
2. A real Paper with the jar, started and stopped by the script, which fails on any error about the plugin:
   ```sh
   python3 -I .claude/scripts/paper_smoke.py --game 26.3 --plugin spigot/build/libs/allay-spigot-dev.jar --modrinth placeholderapi --modrinth plan --command "papi list" --expect "registered internal expansion: allay" --expect "Registered extension: Allay" --ignore 'Plan\] Failed to enable geolocation'
   ```

   The NeoForge mod the same way, on a clean NeoForge server installed into `~/.cache/neoforge-smoke` (`neoforge_smoke.py` is this repo's, made like `fabric_smoke.py`):

## Platforms

How the family ships a project to more than one platform. A project that builds only for Paper keeps its jar's present name until it gains a second platform, so links and Moonlands' `jars.txt` keep working.

- **Modules.** One Gradle module per platform, `paper/`, `fabric/`, `neoforge/`, next to a `core/` module with what they share: the rules as plain Kotlin without game imports, data, and assets. Every module builds from one version, and one release ships them all.
- **Jars.** `<name>-paper-X.Y.Z.jar`, `<name>-fabric-X.Y.Z.jar`, and `<name>-neoforge-X.Y.Z.jar`, each attached again without the version, so `releases/latest/download/<name>-<platform>.jar` always fetches the newest.
- **Modrinth.** One project for every platform. Each platform is its own version, numbered `X.Y.Z+paper`, `X.Y.Z+fabric`, or `X.Y.Z+neoforge`, with its own loaders and dependencies; a mod's version says it runs on the client and the server.
- **Hangar.** Paper only, numbered `X.Y.Z`.
- **Moonlands** runs the Paper jar only.

Allay keeps `spigot` where the family says `paper` (the owner decided on 2026-10-23): the module, `allay-spigot-X.Y.Z.jar`, and Modrinth's `X.Y.Z+spigot`. The mods run on either side, so their Modrinth versions say `client_or_server`. Between `core` and the mods sits `modcore`, what both mods share, so `fabric` and `neoforge` stay thin (the owner decided on 2026-10-24).

## Mods

Two mods for 26.3, on Fabric and NeoForge, built without remapping (the game ships unobfuscated). Each builds the core's `Allay` for each server the game starts, a dedicated one or the one under a singleplayer world, and drops it when that server stops; a singleplayer game may start many. Kotlin and the libraries are shaded and relocated under `chat.allay.libs`, as in the plugin, so a player needs only Fabric API on Fabric and nothing on NeoForge.

### modcore

What both mods share: the game without a loader, compiled against NeoForm's Minecraft through ModDevGradle (`neoFormVersion`, no NeoForge). `fabric` and `neoforge` take its classes and resources into their jars and their dev runs; neither copies its code. It never imports a loader's API: what differs goes through `Loader`.

| Path | What it does |
|---|---|
| `modcore/…/Mod.kt`, `Loader.kt` | `Mod` starts and stops Allay with each server, registers `/ask`, `/askall`, `/askx`, `/allay` with Brigadier (the words after them go to the core's `Commands`), and takes joins, quits, chat mode, and ticks from the loader's entry. `Loader` is what a loader hands in: its id (the backend's `loader`), its name for `get_server`, Allay's version, `config/`, the mod list, its own ingredients, its permissions API, and loader-only integrations |
| `ModPlatform.kt`, `Asker.kt` | `ModSender` and `ModPlayer` (follows the player by UUID: a respawn makes a new `ServerPlayer`), `ModScheduler` (work at the end of a server tick; `main` on the next tick, as Bukkit's `runTask`), `Folders`, `ModEffects` (sounds and particles by Bukkit's names or the game's ids) |
| `ModGame.kt` | `Allay.Game` in the mods: the tools, the stores, what `/allay cancel` hides; `loader` from `Loader`, `side` `server` or `integrated` |
| `Hooks.kt`, `mixin/` | The game's events as listener lists, cleared when a server stops. The loader's events where they exist (each `AllayMod` hands them in), narrow mixins where they don't, on both loaders: a dying player's drops, picking up, an advancement's criterion, a change of the game's language, a furnace's smelt, a stand's brew. Placing a block and a death come from Fabric's own mixins (`fabric/…/mixin/`) and from NeoForge's events, which a claims or revive mod may cancel after a mixin would have fired. Accessor mixins read what the game keeps private (display entities, recipes' results, furnace and stand state, a spawner's mob) |
| `Texts.kt`, `Windows.kt`, `Sounds.kt` | `§` text as the game's components and back, `Window` as the game's dialog, a sound only one player hears |
| `Perms.kt`, `Vanish.kt`, `Claims.kt`, `Placeholders.kt` | Permissions through the loader's API, else `plugin.yml`'s defaults (`Permissions.byDefault`) with operators at level 2, and the singleplayer world's owner as admin; Vanish on Fabric and Vanishmod on NeoForge; claims from Flan, Open Parties and Claims, and Common Protection API (Fabric); Text Placeholder API and its NeoForge port. Each optional, asked only when its mod is loaded |
| `Elsewhere.kt` | What the mod in a player's game says on a server without Allay (`messages.not_on_this_server`), and whether the server's command tree has any of the four commands; each loader's client registers them and feeds the tree |
| `tools/` | The client tools in the mods, one file per Bukkit file with the same tools. `BlockAt` is Bukkit's `Block`, `Worlds` names ids and worlds as the model reads them, `ItemStacks` turns the game's items into `ItemData` as Bukkit's item meta sees them, `Ghosts` draws display entities only one client knows about (marks, drafts, picking), `Recipes` reads the server's recipes |
| `automation/`, `menus/`, `GameClicks.kt` | Automation, the chest windows, and the buttons that reach into the world, as on Bukkit |
| `modcore/src/gametest/` | The game tests both mods run, with real survival players (`Players.survivor`), one class per group. They name `GameTest` from their own package: Fabric's typealias to Fabric API's annotation, or `src/gametestPlain`'s for NeoForge, which also holds a claims mod for the tests (`Claim`); Fabric's `Claim` sits behind Common Protection API |

### Fabric

| Path | What it does |
|---|---|
| `fabric/…/AllayMod.kt`, `OnFabric.kt`, `mixin/` | The entry: Fabric API's events to `Mod` and `Hooks`, and the two mixins for what Fabric API has no event for (`PlaceMixin`, `DyingMixin`, in `allay.fabric.mixins.json`); `OnFabric` is the `Loader` (Fabric Loader's mod list, `FabricIngredient`, fabric-permissions-api, Plan) |

| `fabric/src/gametest/` | Fabric's `GameTest` and `Claim` for the shared tests, the test environments, and the singleplayer client test (`SingleplayerClientTest`) |

### NeoForge

| Path | What it does |
|---|---|
| `neoforge/…/AllayMod.kt`, `OnNeoForge.kt` | The entry (`@Mod("allay")`): NeoForge's events to `Mod` and `Hooks` (chat at `HIGHEST`; a placed block and a death at `LOWEST` unless cancelled; a break a tick later if the block is gone, as Fabric's `AFTER`; a left click on its `START`, giving the client the block back when Allay takes it); `OnNeoForge` is the `Loader` (FML's mod list without `minecraft` and `neoforge`, `Ingredient.isCustom`, NeoForge's PermissionAPI). Allay registers a node for every permission at `PermissionGatherEvent.Nodes`, from `Permissions.all` and the tiers in `config/allay/config.yml` then |
| `neoforge.mods.toml` | Only NeoForge and the game required; modcore's `allay.mixins.json` and the client's `allay.client.mixins.json`; the dev version is `0.0.0-dev` |
| `neoforge/src/client/` | `AllayClient` (`@Mod(dist = CLIENT)`): the four commands through `RegisterClientCommandsEvent`, only while the server's tree has none of them. `CommandMergeMixin` reads that tree at the top of NeoForge's `ClientCommandHandler.mergeServerCommands`, which asks for the client's commands right after |
| `neoforge/src/gametest/` | The `allay_gametest` dev mod: `AllayTests` registers every shared test as Fabric API would (functions, environments, and instances in code, in the 8×8×8 `empty` structure), `NeoForgeGameTests` checks PermissionAPI, and `ClientCheck` is the singleplayer check of `runClientGameTest` |

Rules on top of the ones above:

- Every tool keeps its name, arguments, result, errors, and summaries exactly as on Bukkit: the model must not tell where it runs. `CLIENT_TOOLS` in core lists them; `ToolsTest` and the game tests hold every platform to it. A change to a tool goes into `spigot` and `modcore`, and pure logic into core.
- Bukkit's view of the world is the reference: a stack's own components where Bukkit reads item meta, a block's corner where Bukkit reads `block.location`, `level.maxY` inclusive where Bukkit's `maxHeight` is exclusive. Worlds are named by dimension (`overworld`), since the mods have no world folders.
- What only the asker may see goes by packet to them alone (`Ghosts`, `Trails.particles`, `Sounds`), never into the world.
- The game signs chat: chat mode can't change a line on its way, so `~text` goes out again as a plain line from the player (`ChatMode.say`).
- A server's files: `config/allay/` (`Platform.shared`) holds everything that goes with the license, shared by every singleplayer world; a singleplayer world's save holds only `allay/server-id`.
- Without a claims mod nothing is claimed, but an unopened structure chest stays closed; on a dedicated server the game's spawn protection counts for building, as `Claims.mayBuild` says.
- The mods add no blocks, items, or registries, so a game with one joins any server and any game joins a server with one. The `client` side (a mod working for a player on a server without Allay) is not built: there it only says it can't work.
- A singleplayer world's owner may link and reload without cheats (`Perms.owner`), but operator tools still need operator rights.
- A new event goes through `Hooks`, fed by both loaders' `AllayMod` or by a mixin in modcore, so both mods see the same moment. A loader-only difference goes into `Loader`, never into modcore's code as an `if`.
