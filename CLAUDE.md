# Allay for Minecraft: notes for AI agents

The Minecraft plugin of Allay. `/ask` asks the AI helper a question, `/askall` asks in front of everyone, `/askx` turns a request into commands, and chat mode (`/allay chat`) sends whatever a player writes in chat to Allay. The plugin streams the answer from Allay Server (allay-ai/server) over protocol v2, runs the game tools the agent asks for, and shows a live Claude Code style status while it works. README.md is the shop window (what Allay gives, how to start, links), README.RU.md its Russian copy, MODRINTH.md the Modrinth page. The manual for players, server owners, and developers is the GitHub wiki (https://github.com/allay-ai/minecraft/wiki, English only, cloned from `allay-ai/minecraft.wiki.git`); read it first.

## Talking to the owner

- Reply in Russian, address the owner as «вы». Quotes «ёлочки», an em dash with spaces « — ».
- Code, comments, commit messages, and `config.yml` are in English. Player-facing texts live in `core/src/main/resources/lang/<code>.yml` (en, ru, es, pt, de); a new text goes into every one of them, and `LangTest` checks that each has every English key. README.md is English; README.RU.md follows Russian typography. Change both READMEs and MODRINTH.md together. A new command, permission, config key, or feature also goes into its wiki page (“Commands and permissions”, “Configuration”, and so on).

## How it fits together

Two Gradle modules. `core` holds everything that doesn't touch a game platform and never imports `org.bukkit` or `net.minecraft`; `spigot` is the plugin for Spigot, Paper, and their forks, an adapter around `core`. A future Fabric or NeoForge port is another adapter next to `spigot`, not a second copy of the plugin.

| Path | What it does |
|---|---|
| `core/…/Service.kt`, `Sse.kt`, `Protocol.kt` | Sends a question to `POST /api/v2/chat`, reads the SSE stream, runs the client tools through `Host.onMain`, posts their results back; falls back to v1 when the backend has no v2. `Host` is what a platform gives the backend client: its log, versions, the tools' context, the main thread |
| `core/…/Asker.kt`, `Run.kt`, `Status.kt` | Who asked, one question in flight, and the live status line: spinner, rotating verbs, elapsed time, tokens read (↑) and written (↓) |
| `core/…/Lang.kt`, `GeoIp.kt`, `Yaml.kt` | Each reader's language: `lang/<code>.yml` (in `core/src/main/resources`) with `{name}` placeholders and `{n|one|other}` plurals, picked by the country of the IP (DB-IP, downloaded into `geoip/`), then the game's language, then `locales.default`. `YamlConfig` reads YAML with SnakeYAML exactly as Bukkit's `FileConfiguration` did; `YamlTest` in `spigot` holds it to that |
| `core/…/Config.kt` | `config.yml` as settings. Sounds and particles stay names; the platform resolves them |
| `core/…/Billing.kt`, `BillingNotices.kt` | Who asks and who pays. `Credentials` adds `Authorization: Bearer` (`server.token` for a self-hosted backend, else the license) and, in byok, `X-Provider-Key` to every backend request through an OkHttp network interceptor, and the `provider` block to the body; `Identity` gets a byok server its free license on a hosted backend (since 6.0); `License` is `license.key`; `Billing` calls `/api/v2/license`; `Secrets` masks; `Announcements` decides what operators hear and keeps it in `subscription.json`; `QuotaBar`, `BillingDates` |
| `core/…/Chat.kt`, `PlayerSettings.kt` | `Permissions`; chat mode's routing by the first character (`!`, `?`, `~`). Each player's settings, part of their state on the backend; the random `server-id` that names the server's shared thread of public questions |
| `core/…/tools/` | What tools share on every platform: `ClientTool` and `ToolRegistry`, `ItemData` with `compact()` and `Items.detail()` (an item as the model reads it), `Facts`, `Dimensions`, `Mechanics` (vanilla formulas and tables, with tests), goals (the book; the backend keeps them), reminders, books, buttons and their store, time zones, `QuickNote` (coordinates in `/allay memory`), the `Death` the backend gets, and `Guide` (the commands and prefixes `get_allay_guide` lists; a new command or permission goes there too) |
| `spigot/…/Zygote.kt` | Plugin entry: `/ask`, `/askall`, `/askx`, and `/allay` with its subcommands and tab completion; builds the core's pieces and the `Host` |
| `spigot/…/Handler.kt`, `Animator.kt`, `Executor.kt` | Runs questions for Bukkit senders. A public question (`visibility: "public"`) and its answer go to everyone online; status, tool lines, buttons, and errors stay with the asker. The action bar, sounds, and particles; `/askx` commands as the player, minus `blocked_commands` |
| `spigot/…/BillingCommands.kt`, `BillingWatch.kt` | `/allay link`, `/allay status`, `/allay locale`, `/allay init` (the admin panel's setup link, `core/…/AdminSetup.kt`), and the operator's hint under a billing or provider error; the 5-minute poll of the subscription and its notes to operators |
| `spigot/…/Placeholders.kt` | PlaceholderAPI, optional: what fills `{papi:…}` in texts (`Lang.about`; `Locales.of` sets the reader, `broadcast` the asker) and the `%allay_…%` expansion, registered on the first tick since Allay loads before it |
| `spigot/…/tools/Drafts.kt`, `DraftTools.kt`, `RedstoneTools.kt` | Drafts of builds as ghosts, checked layer by layer (`show_draft`), and the redstone debugger (`inspect_redstone`) |
| `spigot/…/Claims.kt` | GriefPrevention, optional: `Claims.mayOpen(player, container)`, whether the asker could open a container themself |
| `spigot/…/Vanish.kt` | Vanished players: the Bukkit metadata `vanished` that SuperVanish, PremiumVanish, and Essentials set. `Vanish.visible(viewer, other)` decides whether the asker may learn about another player |
| `spigot/…/Plan.kt` | Plan, optional: the `DataExtension` behind Allay's block on players' pages and in “Plugins Overview”. Plan calls it off the server thread, so it reads only thread-safe state (`Locales.known`, `Goals.snapshot`, `BillingWatch.status`); registered on the first tick and again on `/plan reload`. Labels are English: Plan's panel is for admins. Never a key, a license, or dollars there |
| `spigot/…/ChatMode.kt`, `Locales.kt`, `MemoryCommands.kt`, `PrivacyCommands.kt` | Chat mode's events, the join reminder, the tip under a second `/ask`; each player's language from their login; `/allay new`, `/allay memory`, `/allay forget`; `/allay privacy` (a player's data: what's kept, export for admins, erasure, and the consent notice with its buttons before a first question) |
| `spigot/…/tools/` | The client tools on Bukkit. They run on the server thread and see only the asking player and the world around them; other players appear only as a count, or as the asker's locator bar shows them (`Locator`, `get_nearby_players`, and `point_to` with `player`). Each can be switched off in `config.yml`. `ItemStacks.kt` turns Bukkit items into `ItemData`. `ActionTools` change nothing that matters (compass, sorting, a ping, reminders); `LookTools` (`look_at`) reads whatever is under the crosshair, `InspectTools` searches and inspects items and containers, `CareTools` gear, XP, food; `GoalTools` and `Goals.kt` the goals' boss bars and events; `OperatorTools` change the game and are operator-only |
| `core/…/tasks/Tasks.kt`, `core/…/tools/Storage.kt`, `Pins.kt`, `Workshop.kt` | Automation agents as data (`Task`, `TaskBook` with the per-player limit and depth 2, `Reservations`), and the planners with tests: chest layouts (sort, group by category with overflow, move), pinned inventory slots, fuel and furnace shares, and crafting with parts |
| `core/…/Quota.kt`, `spigot/…/QuotaGate.kt` | Spending limits by tier (`QuotaSettings`, `QuotaBook` in `quota.json`, `Quotas.check`) and models by tier (`ModelTiers`); the gate in front of every question and wake, and the admin's note on join when the quota config is wrong. Tiers are weights over the players active this month, the budget opens by day |
| `spigot/…/automation/` | Automation agents on Bukkit: `Automation` runs the wakes (mode "task"), pauses and stops agents; `Picking` the left-click picking; `Blocks` and `Sources` what may be used and where ingredients come from; `Chests`, `Furnaces`, `Stands`, `Crafting` the tools; `Jobs` the furnace and brewing jobs the game drives; `TaskTools` start_task, message_task, cancel_task, say, wait, finish, pick_blocks |
| `spigot/…/Clicks.kt`, `menus/` | Buttons under answers (`add_buttons`, books, the chat mode tip) and what each does when pressed; the recipe, brewing, anvil plan, enchanting, and villager windows, opened from buttons, and the settings window of `/allay`, which holds settings only |

The contract with the backend is `docs/protocol-v2.md` in allay-ai/server. Change both sides together.

## Coming from MCBuddy

Allay was MCBuddy until 4.0.0. Since 6.7 the plugin no longer moves `plugins/mcbuddy-spigot/` by itself: a server coming straight from MCBuddy runs Allay 6.6 once first. The backend still accepts the 3.x tool names `get_buddy_guide` and `buddy_settings`.

## Rules that keep it working

- Spigot API only (`org.spigotmc:spigot-api`), so the jar runs on Spigot and Paper. Watch for types that differ between them: `GameRule` is an interface in Spigot and a class in Paper, so read rules through `Registry.GAME_RULE`. One exception: Paper leaves out Spigot's dialog API (BungeeCord's `net.md_5.bungee.api.dialog`), so windows (`Window` in core) go through `Windows`, which draws them with `spigot/src/paper/` (compiled against paper-api, loaded only on Paper) or with Spigot's API elsewhere. A dialog that doesn't pause the game: `NONE` after an action needs `pause(false)`.
- Bukkit calls happen on the server thread; network calls never do. Chat arrives off it: `ChatMode` only decides and cancels there, then hands the line to the server thread.
- A player's own words go into a template through `Minecraft.withText`, so an `&` they typed never becomes a color.
- PlaceholderAPI goes through `{papi:…}` in the template only, filled in `Lang.fill`'s single pass. Never run `%…%` replacement over a finished line: a player's question or the model's answer could then read other players' data through PlaceholderAPI. `%allay_…%` may be asked from TAB's thread, so it reads only thread-safe state.
- A vanished player never shows through Allay to anyone but themself and operators: anything that counts, names, sees, or completes players goes through `Vanish.visible` (on the server thread, where metadata lives). Their public question goes private (`Handler.ask`), since everyone would read their name. An operator tool may still target them by name.
- Containers reach the model, and glow, only when the asker could open them (`Claims.mayOpen`): outside a GriefPrevention claim or with container trust in it, and never an unopened structure chest, which Paper's anti-xray hides. Every tool that reads or marks a container asks it.
- Redstone and drafts read the world only where the asker may build (`Claims.mayBuild`: outside claims, or with build trust). A draft lives in memory (`Drafts`), one per player, drawn with the same display entities as marks; its size limit (20×15×20) is the owner's, so the model can write it.
- Marks (`Marks`, `show_marks`) are display entities: hidden by default and shown to the asker alone, never persistent, gone on time, `/allay cancel`, quit, and disable. They glow through walls, so `Marks.secret` (ores, spawners, vaults) never glows; keep that list in step with what anti-xray hides.
- Other players reach the model only through `Locator`, the game's locator bar rules (26.3's `ServerWaypointManager` and `WaypointTransmitter`): a name, a distance, and a direction, for players on the asker's bar. The owner allowed exactly that, since the player sees it anyway; never add their coordinates, inventories, or anything the bar doesn't show. Read the rules again from the jar when the game version moves.
- A tool that creates items or changes the world is an operator tool (`operator = true`). The registry offers it only to operators, `Service` refuses it for anyone else, and the tool checks `isOp()` once more. Keep all three checks; non-operators must not be able to get gear through the assistant.
- Automation is the owner's other exception: its tools move and craft for non-operators, but only the player's own things. They touch only containers `Claims.mayOpen` allows, and furnaces, stands, and crafting tables within `automation.radius` and in plain sight (`Blocks.sees`, glass counts as solid). Crafting needs a real crafting table and uses server recipes with plain ingredients only; nothing comes from nowhere. Never inside shulker box items (a placed shulker box is a chest like any other, and takes no shulker box). Chests open in someone's window stay out; chests with a hopper on them (a sorter's input) only take things in: `Blocks.unsuitable(adding = true)`. Water bottles come only from the player's glass bottles at water or a cauldron near, which loses a level a bottle, as in the game.
- Chest changes are planned in memory, checked (totals equal, everything fits, nothing changed since the read), and written in one tick; otherwise nothing moves. Keep `Storage` the only place that plans them, with its tests. `Undo` keeps each player's last five changes, chest plans and inventory sorts, and puts back the newest only while nothing it touched changed.
- Furnace experience goes to the player only when the furnace's store can be emptied (`setRecipesUsed`, Paper); on Spigot it stays in the furnace, so it's never paid twice.
- An agent never gets operator tools (`Service` drops them for task runs and refuses them again). Whatever it plans to take later goes into `Reservations`; when it's gone at the next step, the agent stops and tells the player (`Automation.interfered`).
- One deliberate exception: `[Взять книгу]` gives anyone the written book with the assistant's own long answer, once per book. The owner allowed it: a book of text is no gear. Don't extend it to other items.
- Windows (`menus/`) only show pictures. `MenuListener` cancels every click, drag, and hopper move on a `Menu`; keep it that way, or the windows become a dupe.
- Buttons run `/allay do <id>`. Ids belong to the player who got them (`ButtonStore`) and expire after an hour, so a typed command can't trigger an action nobody offered.
- Keep tool results compact: they cost tokens on every call. Spots are absolute `x`, `y`, `z` with `distance` and `direction` (`Facts.place`); dimensions are the game's ids through `Dimensions`.
- Kotlin, kotlinx, OkHttp, Okio, the MaxMind reader, and SnakeYAML are shaded and relocated under `chat.allay.libs`.
- Every request to the backend signs in (server 6.0): keep `Credentials` on the client as a network interceptor, so nothing goes to another host, redirects included. A new backend call goes through that client. A player's data is the backend's per server; the plugin never sends one player's id for another.
- Nothing about a player reaches the backend before they agree to the notice (`Consents` in core, the gate at the top of `Handler.ask`, the notice in `PrivacyCommands`); every way to ask goes through `Handler.ask`. The agreement carries the SHA-256 of the English notice as the jar ships it and the backend's policy revision (6.9): a change to either asks everyone again, with a notice that says what changed; raise `Consents.VERSION` too when the notice says something new. The notice and the age question are windows (`PrivacyCommands`), with one line in chat to open them again. A player from the EU, the EEA, or the US, or from an unknown country, first says their age in neutral bands (`AgeGate.asks`; the owner chose to spare everyone else); it must reach their country's age of consent (GDPR Art. 8, LOPDGDD Art. 7, COPPA; 16 when the country is unknown). The agreement goes with `age_confirmed`, and one without it asks such a player again; too young keeps only a sealed note in `ages.bin` for a year. With allay.chat (no `server.token`) neither `privacy.consent` nor `geoip.enabled` may skip any of it.
- Other players reach the model by name only when they agreed on this server (`consented.bin`); anyone else is “Player N” for the run (`OtherPlayers`, `ToolContext.nameOf` and `playerNamed`). A new tool that names another player goes through `nameOf`.
- Full privacy (`Settings.full_privacy`, `/allay privacy full`, the `/allay` window) goes with every question as `player.private` and, for a player who agreed, to `PUT /api/v2/users/{id}/privacy` at once (backend 6.5): the admin panel then knows them by pseudonym only. It hides nothing from the model; memories and the session work as before.
- A player's data on request: `/allay privacy`. An export is a 24-hour link from the backend (6.9), shown only to whoever asked, never in the log; the log never says who asked to be erased.
- No personal data in the plugin's folder (since 6.7). `PlayerData` (core) holds each player's time zone, settings, and goals in memory while they play: it loads them from the backend when a player on `consented.bin` joins (the sealed list of UUIDs that agreed here; nobody else is looked up until they use Allay), sends a change a few seconds later, on quit, and at shutdown, and sends each death as it happens, all off the server thread. Nothing reaches the backend for a player who didn't agree, and their changes leave with them. What can't be sent at shutdown goes into `pending.bin`, AES-256-GCM under a key derived from the license or `server.token`, and out on the next start. A new per-player setting goes into `PlayerState`, never into a file.
- Never log, print, or put into chat the BYOK key, the license, or `server.token`. Mask them with `Secrets.mask` (first 5 and last 4 characters at most) and pass error texts through `Credentials.scrub`. The payment link goes only to the chat of whoever ran `/allay link`, and the admin panel's setup link only to whoever ran `/allay init`; the console's own output is the exception, since the console asked. `license.key` stays out of `config.yml` and is owner-only; never overwrite one that holds something else.
- Billing errors read light and never blame the player (“Allay is taking a break on this server…”); operators get the fix under them. Never show dollars: the subscription's limit is a percentage.
- `core` never imports `org.bukkit` or `net.minecraft`. Where it needs the game, it asks through `Asker`, `Host`, or `ItemData`; don't add a seam only a future platform would use.

## Building and releasing

- `./gradlew build` runs both modules' tests and builds `spigot/build/libs/allay-spigot-<version>.jar`, shaded; Java 25. Nothing in the repo holds the version: local builds are `dev`, CI builds on `master` and pull requests are `dev-<sha>`.
- Allay sounds like an allay: `ENTITY_ALLAY_AMBIENT_WITH_ITEM` while thinking, `ENTITY_ALLAY_ITEM_GIVEN` with the answer, `ENTITY_ALLAY_AMBIENT_WITHOUT_ITEM` on errors, each pitch moved by up to `ui.sounds.pitch_variation`. Readers of a public answer hear the answer sound at half volume (`ui.sounds.public_answer`). The game plays these quietly, so 1.0 is the mob's own volume.
- After a change that reaches what the project ships, add it to CHANGELOG.md in the same push: under the topmost “## X.Y.Z” section while that version isn't released (`gh release view vX.Y.Z` fails), or under a new section with the next version: patch for fixes, minor for features, major for breaking changes. A release then needs only the workflow, and the workflow runs only when the owner asks.
- Releases are made by hand when the owner asks, or by the autopilot (below). Add a “## X.Y.Z” section to CHANGELOG.md, push, then run `gh workflow run release.yml -R allay-ai/minecraft -f version=X.Y.Z` (its `changelog` field overrides the section; one of the two must be there; `-f modrinth=true -f hangar=true` also publish there once those projects exist). It builds with `-PreleaseVersion`, tags `vX.Y.Z`, and attaches `allay-spigot-X.Y.Z.jar` to a GitHub release. Watch it with `gh run watch`. Never delete or re-tag a published release.

## Checking a change

1. `./gradlew build`: the tests and the jar.
2. A real Paper with the jar, started and stopped by the script, which fails on any error about the plugin:
   ```sh
   python3 -I .claude/scripts/paper_smoke.py --game 26.3 --plugin spigot/build/libs/allay-spigot-dev.jar --modrinth placeholderapi --modrinth plan --command "papi list" --expect "registered internal expansion: allay" --expect "Registered extension: Allay" --ignore 'Plan\] Failed to enable geolocation'
   ```
   Pass `--game` the version the project targets, and `--build` to pin a Paper build. The script downloads Paper and Modrinth plugins into `~/.cache/paper-smoke` and keeps the server folder when something fails.
3. A question needs a backend and a player. After a release reaches Moonlands, the log shows `Allay X.Y.Z is on`, `papi list` lists `allay`, and the owner asks `/ask` once. Plan's server values show up right away; a player's block fills on their next join or leave. Allay builds against the Spigot API, so it runs on Spigot too; the check uses Paper, which Moonlands runs.

- The wiki names the game and Java versions too (“Installation”, “Building from source”, “Development”): clone `https://github.com/allay-ai/minecraft.wiki.git` and change them with the rest.

## Platforms

How the family ships a project to more than one platform. A project that builds only for Paper keeps its jar's present name until it gains a second platform, so links and Moonlands' `jars.txt` keep working.

- **Modules.** One Gradle module per platform, `paper/`, `fabric/`, `neoforge/`, next to a `core/` module with what they share: the rules as plain Kotlin without game imports, data, and assets. Every module builds from one version, and one release ships them all.
- **Jars.** `<name>-paper-X.Y.Z.jar`, `<name>-fabric-X.Y.Z.jar`, and `<name>-neoforge-X.Y.Z.jar`, each attached again without the version, so `releases/latest/download/<name>-<platform>.jar` always fetches the newest.
- **Modrinth.** One project for every platform. Each platform is its own version, numbered `X.Y.Z+paper`, `X.Y.Z+fabric`, or `X.Y.Z+neoforge`, with its own loaders and dependencies; a mod's version says it runs on the client and the server.
- **Hangar.** Paper only, numbered `X.Y.Z`.
- **Moonlands** runs the Paper jar only.

## Modrinth and Hangar

The projects don't exist yet: create them only when the owner asks (see “Publishing the owner's projects” in `~/c/personal/minecraft/CLAUDE.md`).
